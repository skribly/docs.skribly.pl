# agent-skills

> 39 portable skills that take AI coding agents from a tracker ticket to a reviewed, tested commit - cheap on tokens, safe by default, with no AI co-author trailers.

**agent-skills** is a library of short, tested procedures (“skills”) for AI coding agents, plus a zero-dependency installer that puts them where each agent looks. It supports Claude Code, Codex CLI, Cursor, Gemini CLI, OpenCode, Windsurf, GitHub Copilot and Devin. Skills cover the whole loop: pick up a Redmine, Jira, GitHub, GitLab, Linear or Skribly Tracker issue, plan, branch, implement in stages, test, review, audit and commit. They also cover the specialist jobs around it: Core Web Vitals, load tests, safe migrations, Docker, CI, dependency upgrades, translations and release notes. A group of skills also covers the work around the code: writing a plan as work packages and running a work package task by task, decision records, a release checklist, the check that docs and translations move with a change, and the design review of a page. ![The skills catalogue in Skribly Agent: cards for each skill with its command, group and the agents it is installed for](/_astro/skills-catalog.DRGjq_KS_Z1i9TlW.webp) ## Principles [Section titled “Principles”](#principles) * **Scripts do the mechanical work.** Small Node scripts hand the model a few lines instead of megabytes: a 455 KB Lighthouse report becomes 754 bytes, a 27 KB test log 86 bytes. * **Every risky step waits for your OK.** Commits, comments on tracker issues, screenshots and long test runs are proposed, not done silently. * **Adapts to each project.** The `project` skill detects the stack, the commands and the commit conventions into `.skribly/project.json`, and every skill reads that profile first. Values you set by hand are never overwritten. * **Learns from the work.** At the end of `task`, `test-loop`, `review` and `debug` the agent proposes one confirmed lesson; with your OK, `learn` keeps it in `.skribly/lessons.md` for the next run. Lessons that look like secrets are refused. * **Commits look like yours.** Messages follow the project’s convention, and no skill adds a `Co-Authored-By` or “Generated with” trailer. * **Standalone.** It needs nothing else from Skribly and works in any repository. Skribly Agent is one optional place that uses it. ## Facts [Section titled “Facts”](#facts) | | | | -------------------- | ------------------------------------------------------------------------------------------------------------------- | | Version | 0.3.0 (14 November 2026) | | Skills | 39, in the shared [Agent Skills](https://agentskills.io/specification) format | | Agents | 7: Claude Code, Codex CLI, Cursor, Gemini CLI, OpenCode, GitHub Copilot, Devin (Windsurf installs as Devin Desktop) | | Trackers | Redmine, Jira Cloud and Server/Data Center, GitHub, GitLab, Linear, Skribly Tracker | | Requirements | `git` and Node.js 20 or newer | | Runtime dependencies | None | | Licence | MIT | ## How a skill is built [Section titled “How a skill is built”](#how-a-skill-is-built) Every skill is a folder `skills/<name>/`: 
```text
skills/<name>/
  SKILL.md       at most 110 lines, read when the skill runs
  reference/     extra detail, read only when a step needs it
  scripts/       Node scripts with no dependencies that do the mechanical work
  templates/     files the skill fills in
```
 An agent keeps only each skill’s name and description in its context, one line per skill. The rest loads on demand. ## How it saves tokens [Section titled “How it saves tokens”](#how-it-saves-tokens) 1. **Load on demand.** `SKILL.md` loads when used, `reference/` only when a step needs it. The 110-line limit is enforced in CI. 2. **Scripts instead of the model.** Measured on real projects: | Task | Raw input | Script output | Saved | | --------------------------------------- | ------------- | ------------- | ----- | | Lighthouse report | 455,534 bytes | 754 bytes | 99.8% | | Test run log, 86 tests | 27,098 bytes | 86 bytes | 99.7% | | `npm audit --json` on a 300-package app | 20,555 bytes | 2,126 bytes | 90% | | `git log -60` to learn the commit style | 7,415 bytes | 739 bytes | 90% | | GitHub issue with comments | 8,178 bytes | 1,018 bytes | 88% | 3. **Ask before expensive steps.** Screenshots, Lighthouse runs and full suites need your OK. 4. **Restart instead of dragging transcripts.** `STATE.md` (about 30 lines) holds the goal, what was done and one next step, so you can `/clear` after each stage and resume, in the same or another agent. 5. **Working rules.** The `token-saver` skill gives every agent the same habits: search before reading, read line ranges, never open lock files or build output. The full measurements are on [Token saving](/agent/token-saving/). ## Read next [Section titled “Read next”](#read-next) * [Install](/skills/install/): user scope or project scope, updates, Windows. * [Skills catalog](/skills/catalog/): every skill and when to use it. * [All skills](/skills/skill/): a page per skill, generated from its `SKILL.md`. * [How it works](/skills/how-it-works/): the pipeline, the guardrails, the profile and lessons with scopes. * [Train the skills for your project](/skills/train/): `init`, `train-skills` and the project switches, step by step. * [Supported agents](/skills/agents/): where each agent gets the skills, and the files `agent-skills agent-files` generates from `AGENTS.md`. * [Trackers](/skills/trackers/): credentials for each tracker. * [Commits without AI trailers](/skills/commits/): the three layers that keep commits yours.

# Supported agents

> Where agent-skills installs skills for Claude Code, Codex CLI, Cursor, Gemini CLI, OpenCode, Windsurf, GitHub Copilot and Devin, and how you call them in each. Also the per-agent files that `agent-skills agent-files` generates from `AGENTS.md`.

Every supported agent reads native **Agent Skills** folders: `<name>/SKILL.md` with `name` and `description` front matter, and optional `reference/`, `scripts/` and `templates/`. Seven of them read the same shared folder, `.agents/skills`, so one copy serves Codex, Cursor, Gemini CLI, OpenCode, Windsurf, GitHub Copilot and Devin. Claude Code reads only `.claude/skills`. Locations were checked against each vendor’s documentation on 29 October 2026, and those for Devin and for the project instruction files on 11 November 2026. ## Default format: `--format skills` [Section titled “Default format: --format skills”](#default-format---format-skills) | Agent | Target | Project scope (copy) | User scope (symlink) | Invoke | | -------------- | ---------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------ | | Claude Code | `claude` | `.claude/skills/<name>/` | `~/.claude/skills/<name>` | `/task 123` | | Codex CLI | `codex` | `.agents/skills/<name>/` | `~/.agents/skills/<name>` | `$task 123`, or pick from `/skills` | | Cursor | `cursor` | `.agents/skills/<name>/` | `~/.agents/skills/<name>` | `/task 123` in Agent chat | | Gemini CLI | `gemini` | `.agents/skills/<name>/` + `.gemini/commands/<name>.toml` | `~/.agents/skills/<name>` + `~/.gemini/commands/<name>.toml` | `/task 123` | | OpenCode | `opencode` | `.agents/skills/<name>/` + `.opencode/commands/<name>.md` | `~/.agents/skills/<name>` + `~/.config/opencode/commands/<name>.md` | `/task 123` | | Windsurf | `windsurf` | `.agents/skills/<name>/` + `.windsurf/workflows/<name>.md` | `~/.agents/skills/<name>` + `~/.codeium/windsurf/global_workflows/<name>.md` | `/task 123` or `@task` | | GitHub Copilot | `copilot` | `.agents/skills/<name>/` | `~/.agents/skills/<name>` | `/task 123` in VS Code chat or Copilot CLI | | Devin | `devin` | `.agents/skills/<name>/` | `~/.agents/skills/<name>`; the Devin CLI also reads `~/.config/devin/skills` (on Windows `%APPDATA%\devin\skills`) | `@skills:task` in a prompt | Gemini CLI, OpenCode and Windsurf load skills through a tool or an `@mention` rather than a slash command, so the installer also writes a thin command of a few lines: “use the `<name>` skill with these arguments”. It never duplicates the skill text, so `git pull` and `agent-skills sync` are enough to update. ## Classic format: `--format rules` [Section titled “Classic format: --format rules”](#classic-format---format-rules) For older agent versions: | Target | Written | Notes | | -------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- | | `cursor` | `.cursor/rules/<name>.mdc` (“Agent Requested”) | Project scope only | | `windsurf` | `.windsurf/rules/<name>.md` (`trigger: model_decision`) | Project scope only; the 12,000-character limit per file is checked | | `copilot` | `.github/instructions/<name>.instructions.md`; user scope `~/.copilot/instructions/` | No `applyTo`, so it is not attached to every request | | `gemini` | `.gemini/commands/<name>.toml` with the whole skill inlined | `@{` and `!{` are neutralised so Gemini never injects files or runs commands from skill text | | `opencode` | `.opencode/commands/<name>.md` with the whole skill inlined | | | `claude`, `codex`, `devin` | Same as `skills` | They have no other format | ## Known overlaps [Section titled “Known overlaps”](#known-overlaps) * Cursor, OpenCode and Copilot also read `.claude/skills` at project scope. With Claude and one of those in the same project, a skill may show twice. Install Claude at user scope and the others at project scope, or the reverse. * Codex still loads the deprecated `~/.codex/skills`. agent-skills never writes there, and `agent-skills doctor` warns when old copies shadow the new ones. ## Not fully verified [Section titled “Not fully verified”](#not-fully-verified) * **Windsurf** now prefers `.devin/{rules,workflows,skills}` and reads `.windsurf/*` as a fallback. agent-skills writes `.windsurf/*`, which works in both the old and the renamed app, and the shared `.agents/skills`. * **Gemini CLI** restricts file tools to workspace folders. Skills linked at user scope are activated through `activate_skill`, which grants access to the skill folder. ## Project instruction files [Section titled “Project instruction files”](#project-instruction-files) A repository keeps its instructions for coding agents in one file, `AGENTS.md`. Codex, OpenCode and Devin read it themselves. Claude Code, Gemini CLI, Cursor and Copilot need a small file of their own, and `agent-skills agent-files` generates those files from `AGENTS.md`, so you never write them by hand: 
```bash
cd ~/code/shop                      # a repository with an AGENTS.md
agent-skills agent-files            # write what is missing or out of date
agent-skills agent-files --check    # write nothing, exit 1 when a generated file is missing or differs
agent-skills doctor                 # each agent: configured or not for this repository
```
 Run it again after a `git pull` of agent-skills (new skill versions) or after a change to the structure of `AGENTS.md`. The pointer files contain no instructions, so editing `AGENTS.md` itself needs no re-run. The generator covers seven agents: Claude Code, Codex CLI, Cursor, Gemini CLI, OpenCode, GitHub Copilot and Devin. Windsurf reads `.agents/skills` and `AGENTS.md` too, so a generated repository works there without an extra file. | File | For | Contents | | --------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------- | | `CLAUDE.md` | Claude Code | A marker comment, then the one line `@AGENTS.md` | | `GEMINI.md` | Gemini CLI | A marker comment, then `@./AGENTS.md` | | `.cursor/rules/agents.mdc` | Cursor | An always-applied rule that references `@AGENTS.md` | | `.github/copilot-instructions.md` | GitHub Copilot | A marker comment and a link to `../AGENTS.md` | | `.claude/skills/<name>/` | Claude Code | The skills, copied | | `.agents/skills/<name>/` | Codex, Cursor, Gemini CLI, OpenCode, Copilot, Devin (and Windsurf) | The same skills, once for all | | `.mcp.json` | Claude Code | `{ "mcpServers": {} }`: read-only defaults and an empty server list | | `.skribly/agent-files.json` | The command | What was generated; commit it with the other files | Every text file starts with a comment that says it was generated by `agent-skills agent-files`. Claude Code strips that comment before it reads `CLAUDE.md`, so the agent still sees the single import line. `.mcp.json` never contains a token or a URL with credentials; servers are added by a person. The command is safe to run again and again: * **Twice is the same.** A second run changes nothing and prints `0 change(s)`; line endings do not matter. * **Hand-written files are kept.** A `CLAUDE.md`, `GEMINI.md`, rule, instruction file or skill folder without the marker is reported and left alone, and the command exits 1. Move its content into `AGENTS.md` and delete it, or pass `--force`: the old file is saved as `<path>.bak-agent-skills` first. * **Your own `.mcp.json` servers are kept.** `--force` leaves such a file alone; only `--force-mcp` replaces it, saving the old one as `.mcp.json.bak-agent-skills`. That backup may hold an `env` block with tokens, so delete it or ignore it before `git add`. * **Your own skills are never touched.** Only folders named like an agent-skills skill are managed. * **Everything stays inside the repository.** A link that points outside it is refused, reported and skipped; the command exits 1. * **`--check` and `--dry-run` write nothing.** `--check` exits 1 when a generated file is missing, differs or has no marker, and is the gate to use in CI. `--skills a,b` limits which skills are copied, and `--json` prints a machine-readable report. `agent-skills doctor` lists each of the seven agents as `configured` or `not configured` for the current repository, with the reason, for example `CLAUDE.md missing`. It reports; it does not change anything. The generated files do not yet include the guard hook of each agent or the subagent roles of `.claude/agents/`. ## Agents in Skribly Agent [Section titled “Agents in Skribly Agent”](#agents-in-skribly-agent) Skribly Agent runs 13 agents, more than agent-skills supports. Aider, Amp, Factory Droid, Qwen Code, Goose, Crush and Kimi CLI run in Skribly but have no skill target. See [Supported agents in Skribly Agent](/agent/agents/).

# Commits without AI trailers

> The three independent layers agent-skills uses so commits look like yours - the skills themselves, the Claude Code attribution setting and a commit-msg hook for any tool.

Commits should look like yours. agent-skills uses three independent layers, so one failing does not matter. ## 1. The skills [Section titled “1. The skills”](#1-the-skills) `commit` and `task` write messages in the project’s convention, from `.tasks/workflow.md` or detected from your own recent commits, and never add trailers: no `Co-Authored-By`, no “Generated with”, no agent links or emoji signatures. They commit only after you say OK, stage only the listed files, and never push, merge, rebase or force unless you ask in that conversation. ## 2. The Claude Code setting [Section titled “2. The Claude Code setting”](#2-the-claude-code-setting) 
```bash
agent-skills config attribution off                # ~/.claude/settings.json
agent-skills config attribution off --project .    # this project's .claude/settings.json
agent-skills config attribution status
agent-skills config attribution on                 # undo
```
 It sets `"attribution": { "commit": "", "pr": "" }`, which hides the commit trailer and the pull request footer, and the older `"includeCoAuthoredBy": false` for earlier Claude Code versions. Other keys are kept, a backup is written before the first change, and invalid JSON is never overwritten. ## 3. The git hook, for any tool [Section titled “3. The git hook, for any tool”](#3-the-git-hook-for-any-tool) 
```bash
cd ~/code/shop
agent-skills hooks install
agent-skills hooks status
agent-skills hooks uninstall
```
 The `commit-msg` hook removes: * `Co-authored-by:` trailers. All of them by default; to keep human co-authors, run `git config agent-skills.keepHumanCoauthors true`, and only AI ones are removed. * Footers such as “Generated with Claude Code”, “Generated by GitHub Copilot” or “Made with Cursor”. A “generated, made or created with” line is removed only when it names an AI tool, so “Generated with protoc” stays. It never touches anything else: the subject, the body, `Signed-off-by`, comment lines and everything below the scissors line of `git commit -v` stay byte for byte, line endings included. * Your existing `commit-msg` hook is kept and still runs after this one; uninstalling restores it. * In repositories that use husky, lefthook or another `core.hooksPath`, the installer does not take over that folder. It prints one line to add to your own hook: `node .git/hooks/agent-skills-commit-msg.cjs "$1"`. * The hook needs `node` on `PATH`; without it, the hook skips itself instead of blocking commits. * Hooks are per repository and are not committed. Install it in each clone. Skribly Agent has the same hook built in: **Code & git → Hook without AI trailers**. ## Checking old commits [Section titled “Checking old commits”](#checking-old-commits) 
```bash
git log --format='%h %s%n%b' | grep -inE 'co-authored-by|generated with' | head
```
 Rewriting published history is a team decision; agent-skills never does it.

# How it works

> How the agent-skills skills work together - one pipeline from a plan to a merged branch, read-only guardrails along it, the project profile every skill reads first, and lessons with a scope.

Every step of the work is a skill. Each one reads the project profile (`.skribly/project.json`) and the lessons (`.skribly/lessons.md`) first, keeps its working files under `.tasks/` (out of git), and waits for you at the points marked **OK**. ## The pipeline [Section titled “The pipeline”](#the-pipeline) One path from an idea to a merged branch: 
```text
plan -> spec -> task -> verify -> e2e-check -> improve -> commit -> merge
         \___ review · gate-convention · blast-radius · security-audit · design-review · deslop ___/
```
 Small work skips the early steps: a one-file fix starts at `task`, a task that fits in one sitting needs no `plan`, and a task `task` can describe in five lines needs no `spec`. | Step | Skill | Writes | Waits for | | ---- | --------------------------------------- | ------------------------------------------------ | -------------------------------------- | | 1 | [`plan`](/skills/skill/plan/) | `.tasks/plans/<slug>.md` | **OK** on the plan | | 2 | [`spec`](/skills/skill/spec/) | `.tasks/specs/SPEC-<slug>.md` | **OK**, then `Status: approved` | | 3 | [`task`](/skills/skill/task/) | a branch, code in phases, `.tasks/<id>/STATE.md` | **OK** before the branch | | 4 | [`verify`](/skills/skill/verify/) | nothing: a pass or fail per step | - | | 5 | [`e2e-check`](/skills/skill/e2e-check/) | screenshots under the test output folder | **OK** to spend tokens on screenshots | | 6 | [`improve`](/skills/skill/improve/) | one small fix per note | your next note | | 7 | [`commit`](/skills/skill/commit/) | a local commit, no trailers | **OK** on the message and files | | 8 | [`merge`](/skills/skill/merge/) | the merge into `develop`, a push | **OK** before the push and the cleanup | The `project` skill writes the conventions of the two planning folders into the project: `.tasks/plans/README.md` and `.tasks/specs/README.md`, with the naming, what each file holds and the life cycle `draft -> approved -> done -> archived`. ## The guardrails [Section titled “The guardrails”](#the-guardrails) The guardrails are read-only reviews. Each reports its findings first, with `file:line` and a fix, and changes code only when you accept a finding. | Guardrail | Asks | Called from | | --------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------- | | [`review`](/skills/skill/review/) | does the change do what it claims, for every input? | `task` before each commit; `review pr` before `merge` | | [`gate-convention`](/skills/skill/gate-convention/) | does it follow what the project wrote in `AGENTS.md` and the profile? | after each phase of a spec; `task` before a commit | | [`blast-radius`](/skills/skill/blast-radius/) | what outside the diff relies on what changed? | `task` when an export, route, schema, config or shared module changes | | [`security-audit`](/skills/skill/security-audit/) | secrets, injection, authorization, vulnerable dependencies? | `task` when auth, input handling or dependencies change; `deps-update` | | [`design-review`](/skills/skill/design-review/) | does a page pass the design checklist? | `task` for a visible UI change | | [`deslop`](/skills/skill/deslop/) | machine-written noise in the added lines? | `task` before a commit | `review pr` is the one place where every guardrail runs on the same diff: the whole branch against `develop`, written as a draft review that is posted only after you approve it. ## The project profile [Section titled “The project profile”](#the-project-profile) `.skribly/project.json` holds the stack, the commands (install, dev, build, test, lint, typecheck, format), the commit style and language, the base branch, CI and containers. The [`project`](/skills/skill/project/) skill or `agent-skills init` detects it from `package.json` and lock files, `pyproject.toml`, `composer.json`, `go.mod`, `Cargo.toml`, Dockerfiles, CI files, the README and your commit history. * **Read first, everywhere.** Every skill starts from the profile and falls back to its own detection only when the profile is missing. * **Your edits win.** A value you set by hand is never overwritten by a later detection, and a value you delete stays deleted. * **Safe commands.** A package folder goes into a command such as `cd web && npm test` only when its path is made of plain segments; any other folder is left out and reported as `skipped`. In a repository you did not write, every skill shows you the profile’s commands before running them. * **Only the skills that fit.** The profile becomes stack tags (`node`, `php`, `python` and the other runtimes, plus `web`, `backend`, `database`, `docker`, `data`, `skribly-app`). A skill without stacks fits every project; a skill with stacks is installed only where they match. See [Train the skills for your project](/skills/train/). ## Lessons with scopes [Section titled “Lessons with scopes”](#lessons-with-scopes) At the end of `task`, `test-loop`, `review` and `debug` the agent proposes one lesson it confirmed: a command that works, a convention the code does not show, a pitfall that cost time. With your OK, [`learn`](/skills/skill/learn/) writes it to `.skribly/lessons.md` with the date and the skill it came from. Anything that looks like a secret is refused. Each lesson sits under a scope heading, so a skill reads only the lessons for the files it changes: | Scope | Covers | | --------------- | ------------------------------------------------------------------------------------------ | | `## [All]` | any change; lines above the first heading count as `All` | | `## [CI]` | the pipeline files (`.github/workflows/`, `.gitlab-ci.yml`, `Jenkinsfile` and their like) | | `## [<module>]` | a folder name (`cart` matches any `cart/` folder), a path (`src/cart`) or a glob (`*.sql`) | `lessons.mjs for-diff --base <branch>` prints only the lessons whose scope matches the changed files. A lesson that proves itself can be promoted into the profile. ## What feeds every step [Section titled “What feeds every step”](#what-feeds-every-step) * [`project`](/skills/skill/project/): the profile and the work folders. * [`learn`](/skills/skill/learn/): the lessons, each with its scope. * [`guide-tests`](/skills/skill/guide-tests/): what deserves a test and at which level, used by `task`, `spec` and `test-loop`. * [`writing`](/skills/skill/writing/): the style of every text for people, from commit bodies to reports. * [`handoff`](/skills/skill/handoff/): `STATE.md`, so any agent can resume at any step after `/clear` or a usage limit. ## Cheap on tokens [Section titled “Cheap on tokens”](#cheap-on-tokens) An agent keeps only each skill’s name and description in context. `SKILL.md` loads when the skill runs, its other references only when a step needs them, and small scripts hand the model a few lines instead of raw output. Every skill has a measured size and a budget the repository’s check enforces: [Token cost](/skills/token-cost/). ## Read next [Section titled “Read next”](#read-next) * [Train the skills for your project](/skills/train/): `init`, `train-skills`, switches, lessons and project skills, step by step. * [Agent tooling](/skills/tooling/): the delete guard, the status line, permissions, the MCP smoke test and the CI job. * [All skills](/skills/skill/): every skill on its own page.

# Install agent-skills

> Install agent-skills for one or all seven agents, at user or project scope, keep it updated and remove it cleanly.

## Requirements [Section titled “Requirements”](#requirements) * `git` and **Node.js 20 or newer** (`node --version`). No npm packages are installed: the CLI and every skill script use only Node’s standard library. * At least one supported agent: Claude Code, Codex CLI, Cursor, Gemini CLI, OpenCode, Windsurf, GitHub Copilot or Devin. ## Install in a minute [Section titled “Install in a minute”](#install-in-a-minute) 1. Clone the repository and put the command on your `PATH`: 
   ```bash
   git clone https://github.com/skribly/agent-skills.git ~/agent-skills
   cd ~/agent-skills
   npm link
   ```
 2. Install every skill for every agent, at user scope: 
   ```bash
   agent-skills install --target all
   ```
 3. Turn off Claude Code’s own attribution and check the result: 
   ```bash
   agent-skills config attribution off
   agent-skills doctor
   ```
 4. Restart your agent, or open a new chat, so it reads its skills folder again. Then try `/task 123` in Claude Code or `$task 123` in Codex. On Windows use the same commands in PowerShell with `$HOME\agent-skills`. Folder links are created as junctions, which need no administrator rights. Without `npm link`, run `node cli/agent-skills.mjs …` or `bin\agent-skills.cmd …`. ## User scope or project scope [Section titled “User scope or project scope”](#user-scope-or-project-scope) | | User scope (default) | Project scope | | -------- | ----------------------------------------- | --------------------------------------------------------- | | Command | `agent-skills install --target all` | `agent-skills install --target all --project ~/code/shop` | | Where | `~/.claude/skills`, `~/.agents/skills`, … | `<project>/.claude/skills`, `<project>/.agents/skills`, … | | How | Symlinks to the repository | Copies | | Updates | `git pull`, then `agent-skills sync` | `agent-skills sync` after `git pull` | | Good for | Your own machine, all projects | Sharing with a team through the project’s repository | A project-scope install also detects the project profile, `.skribly/project.json`; pass `--no-detect` to skip it. You can mix them: install everything at user scope and commit `task` and `commit` into a team project so colleagues get them too. Choose explicitly with `--scope user|project`, `--link` or `--copy`. ## Choose skills and agents [Section titled “Choose skills and agents”](#choose-skills-and-agents) 
```bash

```
 `--target` takes `claude`, `codex`, `cursor`, `gemini`, `opencode`, `windsurf`, `copilot`, `devin` or `all`. `--format rules` writes the classic formats for older agent versions; see [Supported agents](/skills/agents/). ## Recommended setup [Section titled “Recommended setup”](#recommended-setup) 
```bash

cd ~/code/shop && agent-skills hooks install    # per repository: strip AI trailers from any tool
```
 Then configure your tracker as in [Trackers](/skills/trackers/). ## Connect a tracker [Section titled “Connect a tracker”](#connect-a-tracker) 
```bash

```
 Credentials come from environment variables or `~/.config/agent-skills/credentials.env`, never from the repository. The first fetch writes `.tasks/<id>/TASK.md`, later fetches print only what changed, and `.tasks/` is excluded locally, so fetched tickets stay out of commits. ## Update and remove [Section titled “Update and remove”](#update-and-remove) 
```bash

```
 Installs are recorded in `~/.config/agent-skills/installs.json` with a hash of each file. `uninstall` removes only what agent-skills installed, keeps files you edited unless you pass `--force`, and deletes folders it leaves empty. # Rule dictionary

> The rules of agent-skills as data - one sentence, a severity and a public source per rule - listed for the files in hand and checked line by line with agent-skills rules --check.

The rule dictionary holds the common mistakes of each technology as data, one file per rule: Node, PHP, Python, Go, Java, databases and migrations, mobile, Docker, CI, infrastructure, data and ML, security, testing and docs, and the frameworks Next.js, React, Vue, Angular, Express, Tailwind CSS, Laravel, Django, Pydantic, SQLAlchemy, Ruby on Rails, Spring Boot, .NET, Kubernetes and Flutter. The `framework-guide` skill reads the rules of the framework at hand; the commands below read them without a skill. Every rule has: | Field | What it holds | | ------------------ | ----------------------------------------------------------------------------------- | | Id | a stable name such as `nextjs/async-request-apis` | | Rule | one sentence | | Severity | `critical`, `high`, `medium` or `low` | | Versions | the framework versions it is for, such as `15+` (optional) | | Applies to | the files it is for, written like `.gitignore` patterns | | Source | the title and address of a public page that says so | | Why, fix, examples | a short reason, the fix, and a bad and a good example | | Check | a one-line pattern that finds the bad case, or the reason why a line cannot show it | ## List the rules [Section titled “List the rules”](#list-the-rules) 
```bash
agent-skills rules --tech docker
agent-skills rules --files src/app/page.tsx,Dockerfile --severity high
agent-skills rules --tech go --json
```
 One line per rule: the id, the severity, the rule and its source. `--tech` keeps the given technologies, `--files` the rules that apply to those files, and `--severity` that level and above, most severe first. ## Check a project [Section titled “Check a project”](#check-a-project) 
```bash
agent-skills rules --check
agent-skills rules --check --project ../shop --tech nextjs,react
agent-skills rules --check --files src/app/page.tsx --json
```
 `--check` runs the rules that carry a line pattern over the project, or over the given files, and prints one line per finding: `file:line rule-id (severity, versions): rule source-address`. The exit code is 1 when there is a finding, so the command fits a CI step. A pattern is at most 200 characters and must match the bad example of its rule and not the good one; some patterns run only in files that import the framework, so code of another library is not reported. The command reads only text: it skips files over 1 MB, binary files, lines past 1,000 characters, dependency and build folders such as `node_modules`, `vendor`, `dist` and `.venv`, and paths outside the project, and it stops at 20,000 files and 1,000 findings. Nothing in the project is changed. A rule whose bad case is something missing, spans several lines or depends on history (a missing `USER` in a Dockerfile, an `await` before a use of `context`, a migration that already ran) has no pattern. It says why in its data, and the last line of the report counts these review-only rules: read them with `agent-skills rules`. ## Read next [Section titled “Read next”](#read-next) * [All rules](/skills/all-rules/): every rule by technology, with its severity and source. * [Agent tooling](/skills/tooling/): the other commands of the CLI. * [`framework-guide`](/skills/skill/framework-guide/): the skill that reads these rules, also in the next release.

# Agent tooling

> Commands of the agent-skills CLI that make coding agents safer and cheaper - a delete guard, a status line, read-only permission presets, an MCP smoke test and a coding agent job for CI.

These commands sit next to the skills without being skills. Each is Node with no dependencies, runs on macOS, Linux and Windows, and every one that writes takes `--dry-run`. | Command | What it does | | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | | `agent-skills hooks install --agent-guard` | a delete guard hook for every agent that has hooks | | `agent-skills guard "<command>"` | says whether the guard would stop a command | | `agent-skills statusline [install]` | one short status line: agent, model, branch, task, session tokens | | `agent-skills permissions [--dry-run]` | allow lists of read-only commands per agent, from `.skribly/project.json` | | `agent-skills mcp-smoke` | starts each configured MCP server, lists its tools, calls one read-only tool | | `templates/ci/` | a coding agent in CI on an issue label: plan, code, review, draft pull request | | `agent-skills init --mcp` | adds the official MCP server of each detected framework to each agent’s project MCP file | | `agent-skills rules [--check]` | the rule dictionary for the files in hand, and its line checks over a project ([Rule dictionary](/skills/rules/)) | | `templates/nightly/` | a nightly report of a repository: checks, audit, outdated packages, agent branches | | `deps-update/scripts/dependabot.mjs` | one Dependabot preset for the detected stack | | `/upgrade` | a major version of a framework or runtime by its migration guide, one area at a time | ## Delete guard [Section titled “Delete guard”](#delete-guard) 
```bash
agent-skills hooks install --agent-guard                 # Claude Code, Codex, Gemini CLI, OpenCode
agent-skills hooks install --agent-guard --agents all    # also Cursor and GitHub Copilot
agent-skills hooks status --agent-guard
agent-skills hooks uninstall --agent-guard
```
 The guard reads each shell command an agent is about to run. These make the agent **ask you** instead of running it: * a recursive or forced delete of the file system root, the home folder or a folder above it, a `.git` folder, anything outside the project or the whole project; * a delete of 20 or more tracked files at once; * `git clean --force`, and `rsync --delete` into those places; * a delete hidden in inline code (`node -e`, `python -c`, `sh -c`, `eval`, PowerShell `-Command`). Deleting a few files inside the project, or ignored folders such as `node_modules` and `dist`, passes. The guard fails closed: an option it does not know counts as recursive and forced, wrappers such as `sudo`, `env` and `xargs` are looked through, and a path it cannot resolve asks. Codex runs hooks only with `codex_hooks = true` under `[features]` in `~/.codex/config.toml`. ## Status line [Section titled “Status line”](#status-line)

 One line such as `claude · Model X · feat/cart · task 482 · 42k tok (21%)`: the agent, the model, the git branch, the task of `.tasks/` whose `STATE.md` names that branch, and the tokens of the session. In a repository you did not write, run `--dry-run` first: the command starts the programs the project configures. ## A coding agent in CI [Section titled “A coding agent in CI”](#a-coding-agent-in-ci) `templates/ci/` in the repository holds a GitHub Actions workflow, a GitLab CI file and `run-agent.mjs`. # Trackers

> Connect agent-skills to Redmine, Jira, GitHub, GitLab, Linear or Skribly Tracker, and use the tasks commands that the task skill runs.

The `task` skill fetches issues with a script (`agent-skills tasks`), so the model spends no tokens on HTTP, pagination or re-reading. The first fetch writes `.tasks/<id>/TASK.md`; later fetches print only what changed: new comments, status, a changed description, new attachments. ## Credentials [Section titled “Credentials”](#credentials) Put them in environment variables or in `~/.config/agent-skills/credentials.env` (Windows: `%USERPROFILE%\.config\agent-skills\credentials.env`). Environment variables win over the file. Start from the template in the repository: 
```bash
mkdir -p ~/.config/agent-skills
cp templates/credentials.env.example ~/.config/agent-skills/credentials.env
chmod 600 ~/.config/agent-skills/credentials.env     # doctor warns if others can read it
agent-skills tasks check                             # who am I, per configured tracker
```
 Never put tokens in a repository, in `.tasks/` or in a chat. Point at another file with `AGENT_SKILLS_CREDENTIALS`. Inside [Skribly Agent](/agent/tasks/), sessions receive these variables from the app, so no file is needed. ## Skribly Tracker [Section titled “Skribly Tracker”](#skribly-tracker) 
```bash
SKRIBLY_TRACKER_URL=http://localhost:8100   # base URL of the instance
SKRIBLY_TRACKER_TOKEN=...                   # Profile -> API tokens
```
 Ids: `ABC-12` or an `/issues/ABC-12` URL on the `SKRIBLY_TRACKER_URL` host. The client uses [REST API v1](/tracker/rest-api/); descriptions and comments are already Markdown, and attachments are downloaded with the same token. “My open tasks” is `assignee=me&status=open&sort=-updated`. ## Redmine [Section titled “Redmine”](#redmine) 
```bash
REDMINE_URL=https://redmine.example.com
REDMINE_API_KEY=...        # My account -> API access key (an admin must enable the REST API)
```
 Ids: `123`, `#123` or an `/issues/123` URL. Comments are journal notes. ## Jira Cloud [Section titled “Jira Cloud”](#jira-cloud) 
```bash
JIRA_URL=https://your-team.atlassian.net
JIRA_EMAIL=you@example.com
JIRA_API_TOKEN=...         # id.atlassian.com -> Security -> API tokens
```
 ## Jira Server / Data Center [Section titled “Jira Server / Data Center”](#jira-server--data-center) 
```bash
JIRA_URL=https://jira.example.com
JIRA_PAT=...               # Profile -> Personal Access Tokens
```
 Ids: `ABC-123` or a `/browse/ABC-123` URL. Wiki markup is converted to Markdown. ## GitHub [Section titled “GitHub”](#github) 
```bash
GITHUB_TOKEN=...           # fine-grained token: Issues read (write only to post comments)
GITHUB_API_URL=https://github.example.com/api/v3   # GitHub Enterprise Server only
```
 Without a token, a signed-in GitHub CLI (`gh auth login`) is used, and public issues work anonymously at 60 requests an hour. Ids: `7` (the repository of the `origin` remote), `owner/repo#7` or an issue URL. ## GitLab [Section titled “GitLab”](#gitlab) 
```bash
GITLAB_TOKEN=...           # read_api (api to post comments)
GITLAB_URL=https://gitlab.example.com   # default https://gitlab.com
```
 Ids: `7`, `group/sub/project#7` or a `/-/issues/7` URL. System notes are skipped. ## Linear [Section titled “Linear”](#linear) 
```bash
LINEAR_API_KEY=lin_api_...  # Settings -> Security & access -> Personal API keys
```
 Ids: `ENG-12` or a `linear.app/.../issue/ENG-12/...` URL. ## Which tracker does an id mean? [Section titled “Which tracker does an id mean?”](#which-tracker-does-an-id-mean) In order: `--tracker`, the `Tracker:` line in `.tasks/workflow.md`, `AGENT_SKILLS_TRACKER`, then whichever tracker is configured. A configured Redmine wins for plain numbers; GitHub or GitLab when the `origin` remote points there. `ABC-12` can be Jira, Linear or Skribly Tracker: the same three settings decide, otherwise the only configured one is used, and with several you are asked. A task fetched once remembers its tracker. ## Commands [Section titled “Commands”](#commands) 
```bash
agent-skills tasks fetch 123                 # TASK.md; on re-fetch only the changes
agent-skills tasks attachments 123 [name]    # images by default, --all for every file
agent-skills tasks list                      # my open issues in every configured tracker (--json)
agent-skills tasks list --local              # tasks in .tasks/ with status, branch and next step
agent-skills tasks comment-draft 123         # create or show .tasks/123/COMMENT.md
agent-skills tasks comment-draft 123 --post --yes    # publish, only after your explicit OK
agent-skills tasks detect                    # git facts used to write .tasks/workflow.md
agent-skills tasks check                     # configuration and token test
```
 ## Safety [Section titled “Safety”](#safety) * Read-only by default. Writing needs `--post --yes`, and the same text is never posted twice. * Tokens are sent only to the tracker’s own host. Redirects to another host, such as a CDN serving an attachment, are followed without credentials. * Behind a corporate proxy with TLS errors, point `NODE_EXTRA_CA_CERTS` at the proxy’s CA certificate.

# Train the skills for your project

> Fit agent-skills to one project step by step - agent-skills init, the train-skills loop, switching skills on and off, lessons with a scope and small project skills of your own.

Training the skills means fitting them to one repository: the right skills for its stack, a checked profile of its commands, and the first lessons the agent proved in it. It takes one command and one conversation, and every step that writes waits for your OK. ## 1. Preview the setup [Section titled “1. Preview the setup”](#1-preview-the-setup) In the project folder: 
```bash
agent-skills init --dry-run
```
 It prints what it would do and writes nothing: the stack and commands it found, the skills that fit the stack, the agents it found and the files it would write. Use `--agents claude,codex` (or `--agents all`) when it picks the wrong agents. ## 2. Run init [Section titled “2. Run init”](#2-run-init) 
```bash
agent-skills init
```
 It does four things and ends with a short summary: 1. Detects the stack, the commands and the conventions into `.skribly/project.json`. Values you set by hand are kept. 2. Installs, in project scope, only the skills that fit the stack, for every agent you use (one copy per agent). 3. Writes `.tasks/plans/README.md` and `.tasks/specs/README.md`, the conventions of the planning folders. 4. Prints what it found and installed. A second run changes nothing. Run it again after the stack changes. To undo all of it: `agent-skills uninstall --target all --project .`. ## 3. Ask your agent to train the skills [Section titled “3. Ask your agent to train the skills”](#3-ask-your-agent-to-train-the-skills) Open the agent in the project and ask for `/train-skills` (`$train-skills` in Codex). The [`train-skills`](/skills/skill/train-skills/) skill finishes the loop: 1. **Reads the profile** with `AGENTS.md` and the README, and asks you once to confirm the commands and the base branch. Your answer is written into the profile by hand, so it wins over later detection. 2. **Runs the checks once**: install (only with your OK), then lint, typecheck and test, the long ones after asking. For each it notes passed, failed with the first real error line, or missing. It does not fix the project’s code here: a failing check is a finding. 3. **Proposes lessons** for the facts it proved, each with a scope and a source, a `file:line` or a commit. At most five, each saved only on your yes. 4. **Proposes project skills** when the project repeats a procedure no installed skill covers. 5. **Reports** in five lines: what init installed, the profile corrections, each check, the lessons saved, the project skills written or proposed. ## 4. Switch skills on and off [Section titled “4. Switch skills on and off”](#4-switch-skills-on-and-off) 
```bash
agent-skills project list                 # every skill: its stacks, whether it fits, installed or disabled
agent-skills project disable wcag-audit   # removed for every agent; init leaves it out from then on
agent-skills project enable load-test     # installed even when the stack does not call for it
```
 Both switches take `--dry-run` and are kept in `.skribly/agent-skills.json`, so the next `init` respects them. A skill without stacks fits every project; the stacks of each skill are on its page under [All skills](/skills/skill/). ## 5. Keep the lessons [Section titled “5. Keep the lessons”](#5-keep-the-lessons) A lesson is one line in `.skribly/lessons.md` under a scope heading: `## [All]`, `## [CI]` or `## [<module>]`, where a module is a folder name, a path or a glob. The agent proposes one at the end of `task`, `test-loop`, `review` and `debug`; [`learn`](/skills/skill/learn/) saves it after your OK, with the date and the skill it came from. 
```text
Lesson (pitfall, scope src/cart, src/cart/price.ts:41): prices are integers in cents; never parse them as floats. Save? [y/N]
```
 Pick the narrowest scope that is still true: every skill then reads only the lessons for the files it changes. Guesses and one-off facts are not lessons, and anything that looks like a secret is refused. Ask `/learn` to list, prune or promote lessons into the profile. ## 6. Add project skills [Section titled “6. Add project skills”](#6-add-project-skills) When the project has a ritual of its own (a release step, a data refresh, a module scaffold), `train-skills` proposes a small skill for it: * named `<project>-<topic>` in lowercase, never the name of a library skill; * one `SKILL.md` in `.agents/skills/<name>/`, with a `name`, a `description` that says when to use it, and at most 40 lines of steps, each citing the file or command it comes from; * shown to you before it is written, and written only after your OK. Claude Code reads `.claude/skills/`, so the agent asks whether it should go there too. Later sessions refine it with `learn`. Nothing is installed or published from it: it stays in the repository, for the people who work in it. ## Read next [Section titled “Read next”](#read-next) * [How it works](/skills/how-it-works/): the pipeline, the guardrails, the profile and the lessons. * [Updates](/skills/updates/): keep the skills current. * [Troubleshooting](/skills/troubleshooting/): `agent-skills doctor` names each problem with its fix.

# Troubleshooting agent-skills

> Fixes for common agent-skills problems - agents that do not see skills, install conflicts, Windows links, tracker errors, the commit hook and optional tools.

## The agent does not see the skills [Section titled “The agent does not see the skills”](#the-agent-does-not-see-the-skills) * Run `agent-skills doctor`: it shows which agents were detected and where skills are installed. * Restart the agent or start a new chat; most agents scan skill folders at startup. * Check the location for your agent in [Supported agents](/skills/agents/). Older versions may need `--format rules`. * Codex lists a skill twice: old copies sit in the deprecated `~/.codex/skills`. `doctor` warns about them; remove them. * Cursor, OpenCode or Copilot list a skill twice in a project: they also read `.claude/skills`. Install Claude at user scope and the others at project scope, or the reverse. ## `agent-skills: command not found` [Section titled “agent-skills: command not found”](#agent-skills-command-not-found) Run `npm link` in the repository, call `node ~/agent-skills/cli/agent-skills.mjs`, or link `bin/agent-skills` into a folder on `PATH` (`ln -s ~/agent-skills/bin/agent-skills ~/.local/bin/`). On Windows use `bin\agent-skills.cmd`. ## “exists and was not installed by agent-skills” [Section titled ““exists and was not installed by agent-skills””](#exists-and-was-not-installed-by-agent-skills) A file or folder with the same name was already there, so it was left alone. Compare it, then rerun with `--force`; the old one is moved to `<path>.bak-agent-skills`. ## `sync` or `uninstall` skips a copy I edited [Section titled “sync or uninstall skips a copy I edited”](#sync-or-uninstall-skips-a-copy-i-edited) On purpose: hand-edited copies are never overwritten or deleted. Keep your edit, or use `--force` to replace or remove it. ## Links on Windows [Section titled “Links on Windows”](#links-on-windows) User-scope installs create folder junctions, which need no administrator rights or developer mode. If a junction cannot be created, for example on some network drives, install with `--copy` and run `agent-skills sync` after updates. ## WSL and Windows at the same time [Section titled “WSL and Windows at the same time”](#wsl-and-windows-at-the-same-time) Each environment has its own home folder and agents. Install in both, from one clone if you like, running `agent-skills install` inside each environment. ## Tracker problems [Section titled “Tracker problems”](#tracker-problems) * `access denied (HTTP 401/403)`: a wrong or expired token, or a missing scope. `agent-skills tasks check` tests every tracker. * `cannot resolve` or `no connection`: VPN or URL. `TLS problem`: set `NODE_EXTRA_CA_CERTS` to your company’s CA certificate. * `ENG-12 could be Jira or Linear` (or Skribly Tracker): add `Tracker: jira` (or `linear`, `skribly`) to `.tasks/workflow.md`, set `AGENT_SKILLS_TRACKER`, or pass `--tracker`. * GitHub without a token: public issues work at 60 requests an hour; private ones need `GITHUB_TOKEN` or `gh auth login`. ## PageSpeed Insights says HTTP 429 [Section titled “PageSpeed Insights says HTTP 429”](#pagespeed-insights-says-http-429) The keyless quota is shared and often used up. Create an API key for the PageSpeed Insights API and set `PSI_API_KEY`, or measure locally with `--local`, which needs Chrome. ## Playwright or axe-core is missing [Section titled “Playwright or axe-core is missing”](#playwright-or-axe-core-is-missing) `browser-check`, `wcag-audit` and `e2e-tests` look for Playwright in the project, then globally. Install it only if you want it: `npm i -D playwright axe-core && npx playwright install chromium`. Without it the skills fall back to manual checklists and say so. ## The commit-msg hook did not run [Section titled “The commit-msg hook did not run”](#the-commit-msg-hook-did-not-run) * Run `agent-skills hooks status` in that repository. Hooks are per repository. * husky, lefthook and similar tools set `core.hooksPath`; add the printed line to their `commit-msg` hook. * `node` must be on `PATH` for git. GUI clients sometimes have a minimal `PATH`. ## Does it send my code anywhere? [Section titled “Does it send my code anywhere?”](#does-it-send-my-code-anywhere) No. The CLI talks only to your tracker (when you fetch, or explicitly post), to OSV.dev or PageSpeed Insights when you run those audits, and to package registries through your own package manager. Nothing else is collected or uploaded. ## How do I use it in a team? [Section titled “How do I use it in a team?”](#how-do-i-use-it-in-a-team) Install at project scope (`--project .`) and commit `.claude/skills` and `.agents/skills`, so everyone gets the same skills. `.tasks/` stays personal. Put shared conventions (base branch, commit pattern, check commands) in `AGENTS.md`, and each developer’s `.tasks/workflow.md` is proposed from them. Each developer installs the commit hook in their own clone.

# Updates

> How to keep agent-skills current - git pull and sync today, and the planned agent-skills update command and plugin marketplaces of Claude Code, Codex and Gemini CLI.

agent-skills is a git repository. Updating it means getting the newer files and letting the CLI apply them to every place it installed skills. ## Update today [Section titled “Update today”](#update-today) 
```bash
cd ~/agent-skills && git pull && agent-skills sync     # every recorded install, user and project scope
agent-skills sync --dry-run                            # what sync would change, without changing it
agent-skills doctor                                    # what is installed where, each problem with its fix
```
 * **User scope** installs are symlinks to the repository, so `git pull` alone updates the skills you have; `sync` re-applies each recorded install. * **Project scope** installs are copies, so they change only when `sync` runs. A file you edited by hand is kept unless you pass `--force`; with `--force` it is first moved to `<path>.bak-agent-skills`. * `sync` re-applies the skills each install already has. A new skill comes with `agent-skills install --skills <name>`, or in a project with `agent-skills init` run again, which adds the skills that fit the stack and keeps your `project disable` and `project enable` choices. Every install is recorded in `~/.config/agent-skills/installs.json`, so `sync` knows every place to refresh. Restart the agent (or open a new chat) afterwards so it reads its skills folder again. ## Planned: `agent-skills update` [Section titled “Planned: agent-skills update”](#planned-agent-skills-update) * **Install without cloning by hand**: `npx github:skribly/agent-skills install --target all`, with no npm package needed. * **`agent-skills update`**: fetches the newest release tag of the repository and runs `sync`, in one command. * **Releases on a tag**: each version is published on GitHub from its tag, with its changelog. ## Planned: plugin marketplaces [Section titled “Planned: plugin marketplaces”](#planned-plugin-marketplaces) The same `skills/` folder will also be described for the agents that install and update skills packs themselves: | Agent | Planned manifest | What it gives you | | ----------- | ----------------------------------------------- | ------------------------------------------------------ | | Claude Code | a plugin and a marketplace (`.claude-plugin/`) | add the marketplace once; Claude Code updates the pack | | Codex CLI | a plugin manifest (`.codex-plugin/`) | Codex installs and updates the pack | | Gemini CLI | an extension manifest (`gemini-extension.json`) | Gemini CLI installs and updates the extension | Until then, `git pull && agent-skills sync` covers every agent. ## Read next [Section titled “Read next”](#read-next) * [Install](/skills/install/): user scope or project scope, Windows, removing everything. * [Train the skills for your project](/skills/train/): `init` and the project switches. * [Changelog](/changelog/): what changed in each release.
