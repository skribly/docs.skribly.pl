# Skribly Agent

> A desktop IDE built around AI coding agents, not around files. What it does, what it needs and where to read more.

**Skribly Agent** is an IDE built around AI agents, not around files. It puts Claude Code, Codex, Cursor Agent, Gemini CLI and nine more side by side like a terminal multiplexer, with tracker tasks, git, pipelines, skills, audits and a preview browser in one window. It runs locally on macOS, Windows and Linux. It replaces five terminals, task descriptions copy-pasted from a tracker into a chat, and one agent’s output pasted into another. It never adds a `Co-Authored-By` trailer nobody asked for. ![The Agents view: a workspace sidebar with three projects and their worktrees, and a Claude Code pane reviewing a diff](/_astro/agent-agents.DhVc-ZmU_Fwbm7.webp) ## In short [Section titled “In short”](#in-short) * **Agents work side by side** in tabs and split panes and tell you themselves when they are waiting for you. * **Tasks come from your tracker as files**, not through copy-paste: `TASK.md` and `STATE.md` per task. * **Agents hand work to each other** through state files and pipelines instead of through you. * **Commits follow your repository’s style** and never get AI trailers, including commits made by agents. * **Everything runs locally.** No account, no telemetry; your agents use their own logins and API keys. ## Facts [Section titled “Facts”](#facts) | | | | ------------------- | ------------------------------------------------------------------------------------------------------------- | | Version | 1.0.37 (6 November 2026); every push to `main` builds a new `1.0.<build>` release | | Systems | macOS 12+ (Apple Silicon and Intel), Windows 10 and 11 (x64 and ARM64), Linux x64 (AppImage, `.deb`, `.rpm`) | | Stack | Electron 45, React 19, TypeScript 7, Vite 8 | | Interface languages | Polish and English, plus any other language through online machine translation that is cached for offline use | | Telemetry | None | | Licence | MIT | ## Requirements [Section titled “Requirements”](#requirements) * `git` in your `PATH`. Without it you can preview files but not see changes. * At least one coding agent, for example `npm install -g @anthropic-ai/claude-code`. Skribly detects installed agents and shows the install command for missing ones. * No separate Node.js. The app runs its helpers with its own runtime. * `ssh` (OpenSSH) only if you want to run agents on remote machines. ## Read next [Section titled “Read next”](#read-next) | Page | What it covers | | -------------------------------------------- | ---------------------------------------------------------------------------- | | [Install](/agent/install/) | Files for each system, first launch, unsigned builds | | [Features](/agent/features/) | Code and git, tasks, pipelines, skills, audits, browser, Docker, CLI and MCP | | [Workspaces and panes](/agent/workspaces/) | Workspaces, tabs, splits, agent states, notifications, worktrees | | [Terminals and sessions](/agent/terminals/) | New sessions, chat mode, resume after restart, SSH, broadcast, hand-off | | [Supported agents](/agent/agents/) | The 13 agents, how to install them and what each one supports | | [Keyboard shortcuts](/agent/shortcuts/) | The `Ctrl+B` prefix and every global shortcut | | [Settings](/agent/settings/) | Every section of **Settings** | | [Accessibility](/agent/accessibility/) | Text size, high contrast, reduced motion, underlined links, focus | | [The skribly command](/agent/cli/) | Control panes and agents from scripts and other agents | | [Audit rules](/agent/audits/) | What the security, accessibility and SEO audits look for | | [Token saving](/agent/token-saving/) | How agent-skills keeps the text sent to the model small | | [Data and network](/agent/data-and-network/) | What is stored, where the app connects, which ports it opens | | [Updates](/agent/updates/) | Auto-update, versions and release files | | [Troubleshooting](/agent/troubleshooting/) | Common problems and their fixes |

# Accessibility in Skribly Agent

> Reading preferences in Skribly Agent - interface text size, high contrast, reduced motion, underlined links and a strong focus indicator - plus keyboard use and themes.

**Settings → Accessibility** holds the reading preferences for the interface. They are saved on this device with the rest of the app’s settings. | Setting | What it does | Default | | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | | **Interface text size** | Scales the whole interface, terminals and the editor included, in steps of 100, 110, 120, 130 and 140 percent. Terminals refit their columns and rows; pages in the Skribly browser keep their own size, so audits and agents measure the real viewport. | 100% | | **High contrast** | Strengthens text and borders in the day and night themes. The terminal and code editor keep their theme colours. | Off | | **Reduce motion** | Stops transitions and animations. # Audit rules

> What the Audits view of Skribly Agent looks for - how the score works, the secret, code pattern and SEO rules, dependency checks, accessibility checks and how findings go to an agent.

The **Audits** view looks at your project and at a running page. Security audits read your project, and accessibility and SEO audits read a running page. This page lists what each audit looks for. The view itself is introduced in [Features](/agent/features/#audits). ## How the score works [Section titled “How the score works”](#how-the-score-works) Every report starts at 100. Each finding lowers the score by its severity, and findings are sorted from most severe. | Severity | Points subtracted | | ------------- | ----------------- | | Critical | 25 | | High | 10 | | Medium | 4 | | Low | 1 | | Informational | 0 | ## Secrets [Section titled “Secrets”](#secrets) The scan covers files tracked by git, up to 1 MB. The value is masked in the report, and lines that look like an example or placeholder are skipped. | Rule | What it detects | Severity | | -------------------- | ---------------------------------------------------- | -------- | | `aws-key` | AWS access key | Critical | | `github-token` | GitHub token | Critical | | `gitlab-token` | GitLab token | Critical | | `slack-token` | Slack token | High | | `stripe-key` | Live Stripe key | Critical | | `google-key` | Google API key | High | | `openai-key` | OpenAI key | Critical | | `anthropic-key` | Anthropic key | Critical | | `private-key` | Private key | Critical | | `jwt` | JWT in code | Medium | | `hardcoded-password` | A password, secret, API key or token set to a string | High | | `env-tracked` | A `.env` file tracked by git | High | ## Risky code patterns [Section titled “Risky code patterns”](#risky-code-patterns) These rules skip test and fixture folders. Every finding has a file, a line and a suggested fix. | Rule | What it detects | Severity | | -------------------- | --------------------------------------------------------------------- | -------- | | `eval` | `eval(…)` in JavaScript, TypeScript, PHP or Python | High | | `new-function` | `new Function(…)` | High | | `inner-html` | HTML inserted with `innerHTML`, `dangerouslySetInnerHTML` or `v-html` | Medium | | `shell-injection` | Shell commands built from interpolated strings | High | | `sql-concat` | SQL built from strings | High | | `unsafe-deserialize` | Unsafe `pickle`, `yaml.load` or `unserialize` | High | | `tls-off` | TLS verification turned off | High | | `weak-hash` | `md5` or `sha1` | Medium | | `cors-any` | Requests allowed from any origin | Medium | | `debug-on` | Debug mode left on in configuration | Medium | | `http-url` | Plain `http://` address of an external system | Low | ## Dependencies [Section titled “Dependencies”](#dependencies) The app reads exact versions from `package-lock.json`, `composer.lock`, pinned `requirements*.txt` and `poetry.lock`, then checks them against OSV.dev. Without a network, the audit still finishes with results from the rules. ## Accessibility [Section titled “Accessibility”](#accessibility) The page loads in a hidden window, and axe-core runs with the WCAG 2.0, 2.1 and 2.2 tags and best-practice rules. # The skribly command

> Control panes and agents of Skribly Agent from outside the window with the skribly command - commands, exit codes, recipes for reviewers and parallel worktrees, and safety.

The `skribly` command lets agents, scripts and you control panes from outside the window. An agent can start a reviewer next to itself, wait for it and read the result. The MCP server, `skribly mcp`, exposes the same operations to agents as MCP tools; it is described on its own page, which is planned. ## How it works [Section titled “How it works”](#how-it-works) * A control API runs inside the app and listens only on `127.0.0.1`, on a random free port. * The port and a random token are written to `~/.skribly/control.json`, readable only by you. Requests without a valid token get `401`. * `skribly` is a Node script with no dependencies. It works only while the app is running. * Sessions started this way appear in the **Agents** view like any other. ## Turn it on [Section titled “Turn it on”](#turn-it-on) 1. Open **Settings → Sessions & control → Local control API**. It is on by default. 2. Under **skribly command**, choose **Install** to add the command to your `PATH`. 3. Optionally install the `skribly` skill in a project. It teaches Claude Code and Codex when and how to delegate work. ## Commands [Section titled “Commands”](#commands) Commands take a target: a session name such as `reviewer`, a pane id, or `current` for the pane you are calling from. Every command prints JSON, and `--text` prints plain text for `read` and `explain`. | Command | What it does | | -------------------------- | ------------------------------------------------------------ | | `skribly status` | Number of panes and agents, and their states | | `skribly workspace list` | Projects, worktrees and the panes in each | | `skribly pane list` | All panes, shells and agents | | `skribly pane create` | Opens a new pane | | `skribly pane run` | Types a shell command and Enter | | `skribly pane read` | Reads the screen as text | | `skribly pane wait-output` | Waits until output matches a regular expression | | `skribly pane rename` | Names a pane for the API | | `skribly pane close` | Closes a pane | | `skribly agent list` | Agents and their states | | `skribly agent start` | Starts a named agent in a new pane, optionally in a worktree | | `skribly agent prompt` | Sends a message, and can wait for the end of the turn | | `skribly agent read` | Reads the agent’s screen | | `skribly agent wait` | Waits for chosen states | | `skribly agent explain` | Shows why the agent is in its state | | `skribly agent stop` | Closes the agent’s pane | | `skribly worktree list` | Lists a project’s worktrees | | `skribly worktree create` | Creates a worktree | | `skribly worktree remove` | Removes a worktree and keeps the branch | | `skribly notify` | Sends a system notification | | `skribly mcp` | Runs the MCP server | | Code | Meaning | | ----- | -------------------------------- | | `0` | Success | | `1` | Error, such as an unknown target | | `2` | Bad usage or no connection | | `124` | Timeout exceeded | ## Recipes [Section titled “Recipes”](#recipes) ### A reviewer next to the implementer [Section titled “A reviewer next to the implementer”](#a-reviewer-next-to-the-implementer) 
```bash
skribly agent start reviewer --kind claude --prompt "Review the changes from git diff."
skribly agent wait reviewer --until done --timeout 600
skribly agent read reviewer --lines 60 --text
```
 ### Parallel worktrees [Section titled “Parallel worktrees”](#parallel-worktrees) Each agent gets its own directory and branch, so they do not overwrite each other’s files. 
```bash
skribly agent start impl-api --kind codex --worktree feature/api-export --prompt "Build the CSV export endpoint per SPEC.md"
skribly agent start impl-ui --kind claude --worktree feature/ui-export --prompt "Build the export button per SPEC.md"
skribly agent wait impl-api --until finished --timeout 1800
skribly agent wait impl-ui --until finished --timeout 1800
```
 ### Wait, then react [Section titled “Wait, then react”](#wait-then-react) `blocked` means the agent is asking for permission or a choice. 
```bash
skribly agent wait impl-api --until done,blocked --timeout 900
skribly agent explain impl-api --text
skribly agent read impl-api --lines 30 --text
skribly agent prompt impl-api "1"
```
 ### Wait for a shell command [Section titled “Wait for a shell command”](#wait-for-a-shell-command) 
```bash
skribly pane create tests --kind shell
skribly pane run tests npm test
skribly pane wait-output tests "Tests:.*(passed|failed)" --timeout 300 --new
```
 ## Safety [Section titled “Safety”](#safety) Other system users cannot read `control.json`, but any process of your own user can. If you do not use the API, turn it off with its switch in **Settings**. The ports the app opens are listed in [Data and network](/agent/data-and-network/#ports). ## Read next [Section titled “Read next”](#read-next) * [Keyboard shortcuts](/agent/shortcuts/): pane, app and editor keys. * [Data and network](/agent/data-and-network/): what listens and who can reach it. * [Features](/agent/features/): the CLI in the context of the other views.

# Data and network

> What Skribly Agent, Skribly Tracker and agent-skills store, which destinations they connect to, which ports Skribly Agent opens and how the apps protect you.

What the Skribly apps store, where it goes and which ports they open. Skribly Agent sends no telemetry and has no server of its own. ## What Skribly Agent stores [Section titled “What Skribly Agent stores”](#what-skribly-agent-stores) | Data | Where | Protection | | ---------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------- | | Tracker tokens | `secrets.json` in the data directory | Encrypted with the system password store. If that is not available, they stay in memory only | | Tracker accounts | `trackers.json` | Plain JSON, no keys | | Settings, projects, layout and pipelines | JSON files in the data directory | Plain JSON | | Disabled MCP servers | `mcp-stash.json` | Plain JSON, which can include keys from the server’s configuration | | Sign-ins in browser tabs | Separate browser profiles | Browser cookies | | Task content | `.skribly/tasks/` in the project | Excluded from git | | Control API token | `~/.skribly/control.json` | Readable only by you, and new on every startup | The data directory opens from **Settings → Updates → Data directory → Show**; see [Settings](/agent/settings/#data-directory). ## Where Skribly Agent connects [Section titled “Where Skribly Agent connects”](#where-skribly-agent-connects) It sends no statistics, crash reports or identifiers. It connects only to these destinations: | Destination | When | What is sent | | -------------------- | ------------------------------------------------- | --------------------------- | | Your trackers | Task list, details, connection test | Token and task queries | | `api.osv.dev` | Security audit with lockfiles | Package names and versions | | `open-vsx.org` | Searching and downloading themes | Search query | | `github.com` | Update checks, which you can turn off | Standard update requests | | Skills repository | Download repository or Sync | `git clone` and `git pull` | | The audited site | Accessibility or SEO audit | Ordinary page requests | | Pages in the Browser | When you open them | As in any browser | | Machine translation | Only for an interface language that is not cached | Interface text to translate | Programs the app runs at your request make their own connections: agents, `git push`, `ssh` and `npx` from MCP settings. ## Ports [Section titled “Ports”](#ports) | Port | Default | Bound to | Who can reach it | | ------------------------ | ------------------------ | ----------- | ---------------------------------------------------------------------------------------------------- | | Chrome DevTools Protocol | Off, `9333` when enabled | `127.0.0.1` | Any program on this computer, without authentication. It sees all tabs, including signed-in profiles | | Control API | On, random free port | `127.0.0.1` | Processes that read the token from `control.json` | ## How the app protects you [Section titled “How the app protects you”](#how-the-app-protects-you) * The interface has no access to Node.js and can call only a fixed list of methods. * Preview and agent tabs run without any access to the app. * Commands run without a shell, with a time limit and an output limit. The exception is `.cmd` and `.bat` files on Windows. * Reading, writing, discarding and searching reject paths outside the project directory. * Extracting packages rejects paths that escape the target directory. * Themes are read as JSON, and extension code never runs. ## Skribly Tracker [Section titled “Skribly Tracker”](#skribly-tracker) * Markdown is rendered with raw HTML escaped and unsafe links dropped. * Attachments stay on a private disk and are served only through authorised routes. * Webhook secrets and API tokens are shown once and never logged. * A viewer’s token never changes data. ## agent-skills [Section titled “agent-skills”](#agent-skills) * The command line talks only to your tracker, and to OSV.dev or PageSpeed Insights when you run those audits. Your package manager reaches its own registries. * Tokens are sent only to the tracker’s own host. Redirects to another host carry no credentials. * The tracker command is read-only by default, and the same text is never posted twice. ## Read next [Section titled “Read next”](#read-next) * [Security](/security/): how to report a vulnerability. * [Features](/agent/features/): all views of Skribly Agent, grouped by job.

# Features

> Everything around the agents in Skribly Agent - the editor, git and commits, tasks and trackers, pipelines, skills, audits, the preview browser, Docker, integrations and the CLI.

Skribly Agent has one view per job, reachable from the sidebar, with `⌘1` to `⌘9` (`Ctrl` on Windows and Linux) or from the command palette `⌘K`. Agents themselves are covered in [Workspaces and panes](/agent/workspaces/) and [Terminals and sessions](/agent/terminals/). ## Dashboard [Section titled “Dashboard”](#dashboard) Agents at work, tasks assigned to you, recent commits and token usage. Token usage is computed locally from the session files of Claude Code and Codex; nothing is sent. ## A real IDE around the agents [Section titled “A real IDE around the agents”](#a-real-ide-around-the-agents) * A Monaco editor with tabs, quick open `⌘P`, search in files `⌘⇧F` (ripgrep), side-by-side diffs and a bottom terminal. * Files changed by an agent reload automatically. * **Agent actions on selected code** (`⌘⇧I`): Explain, Fix, Write tests, Review, sent to a running agent or a new session. * The command palette `⌘K` reaches views, projects, actions and agents. ## Code and git [Section titled “Code and git”](#code-and-git) * Changes and the index, branches, push and pull, a history graph of all branches, and pull requests through the GitHub CLI. * **Commit suggestions without a model.** The pattern is learned from your history (`feat(scope): …`, `[KEY] …`, `KEY: …`, `#123 - …`), with the language, type and scope taken from the changed files and the key from the branch name. The suggestion shows where each part came from. * **Agent** improves the suggested message from the staged diff, when you want it to. * **A commit hook strips AI trailers** such as `Co-Authored-By` and “Generated with…”, including from commits that agents make in their terminals. Turn it on with **Hook without AI trailers** at the bottom of the changes panel. * Sign in to GitHub, GitLab, Bitbucket, Gitea or Azure DevOps to see real commit activity. ## Tasks and trackers [Section titled “Tasks and trackers”](#tasks-and-trackers) * Jira (Cloud and Server/Data Center), Redmine, GitHub Issues, GitLab, Linear and Skribly Tracker in one list, plus local tasks. Skribly Tracker is the default tracker. * **Start with an agent** writes the task to `.skribly/tasks/<KEY>/TASK.md`, creates `STATE.md`, a branch from your pattern (or a worktree) and launches the agent with a ready prompt, so the agent spends no tokens fetching the ticket. * Status changes, comments, assignment, new issues, search and time logging without leaving the app, where the tracker supports them. * Tokens are encrypted with the system keychain. Agent sessions receive them as environment variables named the way agent-skills expects, so `/task 123` works without a credentials file. What each tracker supports in the app: | Tracker | Key | Comment | Status | Assign | Create | Search | Log time | | --------------- | ------------------ | ------- | ------ | ------ | ------ | ------ | -------- | | Skribly Tracker | `AGENT-12` | Yes | Yes | Yes | Yes | Yes | Yes | | Jira | `PROJ-123` | Yes | Yes | Yes | Yes | Yes | Yes | | Redmine | `2047` | Yes | Yes | Yes | Yes | Yes | Yes | | GitHub | `owner/repo#12` | Yes | Yes | Yes | Yes | Yes | No | | GitLab | `group/project#34` | Yes | Yes | Yes | Yes | Yes | Yes | | Linear | `ENG-56` | Yes | Yes | Yes | Yes | Yes | No | `.skribly/` is added to `.git/info/exclude`, so task files never end up in a commit. ## Pipelines [Section titled “Pipelines”](#pipelines) A pipeline is several agents, from different vendors if you like, working toward one goal. * Stages run in order; steps within a stage run in parallel. * Each step is a headless agent that gets its role, the goal and the latest part of `.skribly/runs/<id>/handoff.md`, not the previous agent’s whole conversation. # Token saving

> How agent-skills keeps the text that goes through the model small - loading on demand, scripts for mechanical work, asking before expensive actions, cheap restarts and working rules - with measured numbers.

Usage limits depend on how much text goes through the model. agent-skills keeps that small in five ways. The numbers below were measured on real projects by the agent-skills authors. ## Load on demand [Section titled “Load on demand”](#load-on-demand) An agent keeps only each skill’s name and description in context. The full `SKILL.md` loads when the skill runs, and reference files only when a step needs them. Every `SKILL.md` is at most 110 lines, and a check in CI enforces it. ## Scripts do the mechanical work [Section titled “Scripts do the mechanical work”](#scripts-do-the-mechanical-work) Fetching, parsing, counting and filtering are done by scripts that print only what the model needs. Sizes are in bytes, and four bytes are roughly one token. | Task | Raw input | Script output | Saved | | --------------------------------------------- | --------- | ------------- | ----- | | Lighthouse report | 455,534 | 754 | 99.8% | | Test log of 86 passing tests | 27,098 | 86 | 99.7% | | `npm audit --json` on a 300-package app | 20,555 | 2,126 | 90% | | `git log -60` to learn the commit style | 7,415 | 739 | 90% | | GitHub issue and comments | 8,178 | 1,018 | 88% | | SQL log of one request with an N+1 | 4,204 | 490 | 88% | | `package.json` to find test and lint commands | 2,122 | 275 | 87% | Fetching a task again prints only new comments and changed fields. Failing test runs print the failing blocks with `file:line` and a summary, never the full log. ## Ask before expensive actions [Section titled “Ask before expensive actions”](#ask-before-expensive-actions) A screenshot costs about 1,000 to 2,000 tokens, so `browser-check` asks first and captures only the changed element. Local Lighthouse, full test suites and load tests are proposed, not run silently. ## Sessions that restart cheaply [Section titled “Sessions that restart cheaply”](#sessions-that-restart-cheaply) `STATE.md`, about 30 lines long, holds the goal, what was done, changed files, check results, decisions and one concrete next step. After a stage, clear the session and resume from the file. It is cheaper and more precise than dragging a long transcript along. ## Working rules [Section titled “Working rules”](#working-rules) The `token-saver` skill gives every agent the same habits: * Search before reading, and read line ranges. * Never open lockfiles or build output. * Use short command forms, such as `git status --short`. * Edit instead of rewriting. * Put results first in answers. * Use subagents with narrow briefs for wide searches. ## Read next [Section titled “Read next”](#read-next) * [Skills catalog](/skills/catalog/): all skills. * [Install agent-skills](/skills/install/): set up the skills. * [Features](/agent/features/): all views of Skribly Agent, grouped by job.

# Troubleshooting

> Fixes for the most common Skribly Agent problems - agent detection, terminals, unsigned builds, Linux sandboxing, trackers, worktrees, hooks and audits.

## An agent is not detected [Section titled “An agent is not detected”](#an-agent-is-not-detected) **Symptom:** in **Settings → Agents** the agent shows “not installed”, even though it works in your terminal. 1. Click **Detect again**; the list is cached for five minutes. 2. Check where the agent is: `which claude` (Windows: `where claude`). Skribly searches the `PATH` of your login shell, plus `~/.local/bin`, `/opt/homebrew/bin` and `/usr/local/bin`. 3. If you add the agent’s folder to `PATH` only inside a block for interactive shells, or in a file the login shell does not read, move it to `~/.zprofile` or `~/.bash_profile`. 4. A shell that takes more than five seconds to start cannot return its environment in time. Speed it up, or link the agent into `~/.local/bin`. 5. On Windows, Skribly does not read the shell; the agent must be in the system `PATH`. Restart Skribly after an npm install. 6. Restart Skribly after any change to `PATH`; the environment is read once at startup. ## Claude Code only in the VS Code extension [Section titled “Claude Code only in the VS Code extension”](#claude-code-only-in-the-vs-code-extension) Skribly finds the Claude Code binary from the VS Code, Cursor, Windsurf and VSCodium extensions, from `~/.claude/local`, from `~/.local/bin` and, on macOS, from the Claude app. If it does not, open the editor once after updating the extension so it unpacks the binary, or install the CLI with `npm install -g @anthropic-ai/claude-code`. Claude plugins need a working `claude`. ## A terminal does not open [Section titled “A terminal does not open”](#a-terminal-does-not-open) **Symptom:** **New session** fails with an error about `pty.node`, `node-pty` or `posix_spawnp failed`. * Check that `$SHELL` points to an existing file. Skribly runs `$SHELL` (by default `/bin/zsh` on macOS, `/bin/bash` on Linux), and `pwsh` or `powershell.exe` on Windows. * **First characters disappear:** the agent command is typed 400 ms after the shell starts, and a very slow prompt can lose it. Start the agent by hand in the pane, or speed up the shell. ## `Ctrl+B` does not reach the program in the terminal [Section titled “Ctrl+B does not reach the program in the terminal”](#ctrlb-does-not-reach-the-program-in-the-terminal) That is intentional: `Ctrl+B` is the pane prefix. Change the prefix in tmux or the shortcut in your program. # Updates

> How Skribly Agent updates itself on macOS, Windows and Linux, how versions are numbered, which files each release has, and what happened to the former name.

Skribly Agent updates itself from GitHub Releases. It checks at startup and every four hours, downloads the new version in the background and installs it on the next restart. ## How auto-update works [Section titled “How auto-update works”](#how-auto-update-works) | When | What happens | | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------- | | 8 seconds after startup | The first check, in a built app with **Update automatically** on | | Every 4 hours | Another check | | New version available | Background download; the status bar shows “Downloading \<version> N%” | | Downloaded | The status bar shows “Version \<version> ready — restart”. Click it to install and restart, or the update installs when you quit. | | Error | A message in **Settings → Updates** | | System | What updates | | ------- | ---------------------------------------------------------------------------------------------------------------- | | macOS | The `-mac.zip` package. The app is not signed, so Skribly verifies the package (SHA-512) and swaps it in itself. | | Windows | The NSIS installer. The portable build does not update itself. | | Linux | The AppImage. `.deb` and `.rpm` update by installing the new version. | **Settings → Updates** shows the version, system and architecture, a **Check for updates** button, the download progress, the **Update automatically** switch and the data directory. ## Versions [Section titled “Versions”](#versions) Versions look like `1.0.<build number>`, with release tags like `v1.0.37`. Every push to `main` builds a new version for macOS, Windows and Linux into one GitHub Release, with notes grouped from the commits and a `SHA256SUMS.txt`. Installed apps only see a release once it has files for every system. ## Release files [Section titled “Release files”](#release-files) | System | Files | | ------- | ----------------------------------------------------------------------------------------------------- | | macOS | `Skribly-<version>-arm64.dmg`, `Skribly-<version>-x64.dmg`, plus `-mac.zip` packages for auto-update | | Windows | `Skribly-Setup-<version>.exe` (one installer for x64 and ARM64), `Skribly-Portable-<version>-x64.exe` | | Linux | `Skribly-<version>-x86_64.AppImage`, `Skribly-<version>-amd64.deb`, `Skribly-<version>-x86_64.rpm` | Each release also has stable copies without the version in the name, such as `Skribly-mac-arm64.dmg` and `Skribly-Setup.exe`, so a link to the latest release always gets the newest build. ## Upgrading from the former name [Section titled “Upgrading from the former name”](#upgrading-from-the-former-name) The app used to be called **Skryba Agent Workflow**. Updating to Skribly Agent keeps everything: | What | After the update | | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | | Data directory | An install that already uses the old folder keeps it, so settings, tokens, sessions and sign-ins stay. New installs use `Skribly Agent`. | | Project folders | New work goes to `.skribly/`. Tasks already in `.skryba/` stay there and are still listed and resumed. | | Home folder | `~/.skribly/control.json` is the new location. Worktrees in `~/.skryba/worktrees` stay valid. | | Command and MCP | `skryba` keeps working next to `skribly`. MCP tools are now `skribly_*`; calls to `skryba_*` still work. | | Environment | `SKRIBLY_*` variables come first and `SKRYBA_*` still work as a fallback. | | Saved choices | Themes, tracker accounts, the link scheme, commit hooks and preferences carry over. | On macOS an updated app keeps its old location in **Applications**; only a fresh install from the `.dmg` uses the new name. If you install that way, remove the old app; the data directory stays in use either way.

# Workspaces and panes

> How the Agents view of Skribly Agent is organised - workspaces, tabs, splits and panes - and how agent states and notifications work.

The **Agents** view works like a terminal multiplexer built for agents: workspaces → tabs → splits → panes. Each pane is a terminal or a chat with an agent, with state detection, notifications and resume after restart. ## Layout model [Section titled “Layout model”](#layout-model) | Level | What it is | Where it comes from | | ------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | | **Workspace** | A project directory or one of its worktrees | A pane belongs to the workspace whose path matches its directory best. Sessions outside any project land in **Other directories**. | | **Tab** | A set of panes in one workspace | **+** on the tab bar, `Ctrl+B c` or `⌘T`. Double-click a tab to rename it. | | **Split** | A tree of horizontal and vertical splits | Drag the dividers with the mouse. | | **Pane** | An agent terminal, a shell or a chat | **New session**, split shortcuts, the CLI, pipelines or tasks. | Terminals live in the app’s main process, so switching views or tabs, or reloading the window, does not interrupt them. A reopened pane replays its last output. The layout is saved continuously. When a tab has three panes, Skribly opens the next session in a new tab so panes do not get too narrow. Sessions started from outside, by the CLI, pipelines or tasks, also get a place in the layout. ## Workspace sidebar [Section titled “Workspace sidebar”](#workspace-sidebar) The **Workspaces** sidebar on the left (toggle with its button or `Ctrl+B b`) shows: * one group per project, with a **main** row and one row per worktree (the branch name); * under each workspace, its sessions with the agent’s avatar, its `@name` and its state; click one to go to its pane; * a badge in the header with the number of sessions waiting for you; * **+** next to a project to create a worktree, and a trash icon next to a worktree to remove it. The state of a tab, workspace or project is the most important state among its panes, in this order: *waiting for a decision* → *done* → *working* → *starting* → *ready* → *finished*. ## Pane header [Section titled “Pane header”](#pane-header) | Element | Action | | ----------------------- | --------------------------------------------------------------------- | | Checkbox | Selects the pane for [broadcast](/agent/terminals/#broadcast) | | Avatar and title | Double-click to rename (`Enter` saves, `Esc` cancels) | | `@name` | The session’s name for the CLI and MCP | | Branch | The session works in a separate worktree | | Machine | The session runs on an SSH machine | | **resumed** | The pane was restored after a restart | | State badge | Opens [Why this state?](#why-this-state) | | Hand-off | [Hands the work to another agent](/agent/terminals/#handing-off-work) | | Split right, split down | Opens **New session** next to this pane | | Maximise | Same as `Ctrl+B z` | | Close | Asks first when the agent is working or waiting | ## Agent states [Section titled “Agent states”](#agent-states) | State | Label | Meaning | | ---------- | ---------------------- | ---------------------------------------------------------------- | | `starting` | starting | The session has just been created | | `working` | working | The agent is working: there is activity in its output | | `blocked` | waiting for a decision | The agent asks for approval or a choice and waits for you | | `done` | done | The agent finished its turn and you have not seen the result yet | | `idle` | ready | Result seen; the agent waits for the next prompt | | `exited` | finished | The process has exited | States come from what the agent shows, with no plugins or hooks in the agent: * **The agent’s screen.** Each terminal has an invisible twin that renders the same stream, so Skribly reads the rendered screen rather than raw escape codes. Each agent has rules for *waiting for a decision* and *working*, such as Claude Code’s “Do you want to…?” question or Codex’s approval dialog. Generic rules catch `(y/n)`, “Press Enter to continue” and password prompts. The rules are conservative: a false *waiting for a decision* is worse than a late one. * **Output activity.** With no matching rule, output in the last 1.5 seconds means *working*. After 2.5 seconds of silence the turn ends: *done* if there was real work you have not seen, otherwise *ready*. * **Agent recognition.** Skribly checks the foreground process and the screen, so a plain terminal pane where you start `codex` by hand gets Codex’s avatar and rules. * **Viewing.** A visible *done* pane in a focused window becomes *ready*. * **Process exit.** The session becomes *finished*. ### Why this state? [Section titled “Why this state?”](#why-this-state) Click the state badge in a pane header. The dialog shows the state, the recognised agent, the source (screen pattern, output activity or process exit), the foreground process, the rule that matched and the last 24 lines of the screen. A program that keeps redrawing something, like a clock or a progress bar, shows as *working*. ## Notifications [Section titled “Notifications”](#notifications) | Where | When | | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | | Badge on the **Agents** icon | The number of sessions waiting, or working when nothing waits | | Status bar | “N working · M waiting” | | In-app message | An agent you cannot see asks for a decision or finished its turn | | System notification | An agent asks for a decision, or finished a turn after at least 15 seconds of work, while no Skribly window has focus. Clicking it opens the pane. Plain shells do not notify. | | `skribly notify` | An agent or a script sends one itself | Turn system notifications off in **Settings → Editor & notifications → Notifications**. The agent overview shows every agent’s screen at once. Arrow keys pick a session, and `Enter` or a number opens it. ## Worktrees for agents [Section titled “Worktrees for agents”](#worktrees-for-agents) A worktree is a separate directory with the same git history, so two agents in two worktrees never overwrite each other’s files. 1. In the workspace sidebar, hover over a project and click **+**, or choose **+ New worktree…** in **New session**. 2. Enter the branch and the base. An existing branch is checked out; a new one is created from the base, by default the project’s base branch. 3. Click **Create**. The worktree appears as its own workspace. | Detail | Value | | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | | Directory | `~/.skribly/worktrees/<repo>/<branch>`, or the folder set in **Settings → Sessions & control → Worktree directory** | | Removal | The trash icon runs `git worktree remove` and `git worktree prune`. **The branch is kept.** With uncommitted changes, Skribly asks before forcing it. | | Refresh | Every 30 seconds, so worktrees created in a terminal show up too |
